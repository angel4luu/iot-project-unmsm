## Project

Academic IoT prototype (UNMSM, Grupo 5): one ESP32 node monitors one controlled
single-phase lab load and sends data over MQTT/mTLS to an ingestion service,
InfluxDB/SQLite storage, a Grafana dashboard, and threshold alerts. There are two
tracks:

1. **System**: driven by Spec Kit. Specs are complete; no source code exists yet.
2. **Article**: an IEEE paper in LaTeX under `article/`.

## Source-of-truth order

1. `.specify/memory/constitution.md` (safety, measurement integrity, MVP-first, security, contracts, reproducibility, resilience)
2. `specs/001-energy-monitoring-system/` (spec, plan, research, data model, contracts)
3. `article/SPEC.md`, which is guidance only. If it conflicts with the specs, the
   specs win, and the resolution is recorded in `article/README.md` › Decisions.
   Never leave a conflict silently unresolved in the repo.

Change the system's scope only through Spec Kit commands (spec amendment), never
inside the article or code.

## Before starting any step (wait for approval)

Before starting any phase, milestone, or article step, present a short briefing and
wait for the user to approve it:

1. **Scope**: what the step covers, what it produces (files, sections), and what is
   explicitly left out.
2. **Plan**: the main actions in order (searches, reads, drafts, builds, tests).
3. **Estimated cost**: approximate tokens and tool calls, and the approximate share
   of the Claude session/context it will use (low < 15%, medium 15–40%,
   high > 40%). Label these as estimates; actual usage cannot be measured beforehand.
4. **Codex handoff option**: always offer handing off all or part of the step to
   Codex (bulk searching, scaffolding, repetitive edits, long test runs). Recommend
   it when the step is high-cost, and say what Claude would keep (verification,
   final drafting, review). If chosen, write a self-contained handoff prompt.

Skip the briefing only for trivial edits or when the user explicitly says to go ahead.

## Always update the trackers

After completing, starting, or changing any phase, step, milestone, or decision:

- Update `README.md`: "Status at a glance" (and its last-updated date), the relevant Roadmap row, "Open decisions", and add a short "Recent updates" row. Keep the README short and non-technical; technical detail belongs in `specs/` or `article/README.md`.
- For article work, also update the Status and Decisions tables in `article/README.md`.

## Article rules

- Write the paper in **Spanish**; repo docs and code comments stay in English.
- Class `IEEEtran` (conference). Build with `make -C article` (latexmk to `article/build/main.pdf`); confirm it compiles after each edit.
- The bibliography is active; add only DOI-verified entries (or official statistics checked at source).
- Cite only real, DOI-verified sources in `article/references.bib`; never invent references, statistics, or results.
- Results come only from preserved experiment evidence; tables are generated by scripts. Pending values stay as `\todo{}`.
- Describe the system exactly as specified: active power is the mean of v·i (FR-003); no power-factor or frequency accuracy claim; no energy or cost savings claims; anomaly detection and forecasting are future work.
- One sentence per line in `.tex` files.

## Repo rules

- No secrets, keys, or real endpoints in tracked files (constitution IV).
- `docs/` (lab reports), `.codex/`, and `.agents/` (except `skills/speckit-*`) are git-ignored local material.
- Mains-voltage work requires a qualified-person review before energizing; never suggest skipping it.
